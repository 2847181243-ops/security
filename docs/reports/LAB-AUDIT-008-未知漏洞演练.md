## 1. 目标

按“审计 → 候选漏洞 → 最小 PoC → 分诊 → 修复/披露演练”走一遍，不依赖已知 CVE。

## 2. 范围与环境

- 目标：lab/webapp/server.mjs，127.0.0.1:8099；
- 源码 49 行，Node 24；
- 只读代码 + 本机请求，不打外部。

## 3. 假设

H1：除设计内 XSS/SQLi/IDOR/SSRF 外，还有未标注的输入反射点；H2：/fetch 响应无大小限制。

## 4. 步骤

1. 枚举路由与输入；
2. 标出设计内漏洞（/xss、/login 注入、/idor、/fetch SSRF）；
3. 审 /login 的 SQL 字符串回显；
4. 发 HTML 标签 payload，看是否原样进入页面；
5. 修复：输出转义；回归测试。

## 5. 结果

| 候选 | 结论 |
|---|---|
| /login 回显 XSS | 确认：payload 进入 <pre> 未转义；修复后转义 |
| /fetch 响应无上限 | 候选：代码无 cap；加 1MB 上限后 5MB 响应 413，修复前未做压力测试 |
| /file 路径穿越 | 前一轮已确认并修复，回归 403 |

## 6. 证据

- 证据文件：data/security/experiments/LAB-AUDIT-008/evidence.txt；
- 回归脚本：runtime/security/regress_webapp.mjs；
- 修复：server.mjs 加 esc()，/login 两处回显转义。

## 7. 分析

事实：/login 把 SQL 字符串原样放进 HTML，属于输出编码缺失；/fetch 的 b += c 没有上限，属于资源控制缺失。推断：前者是真实反射 XSS；后者在目标返回大响应时可能造成内存压力，修复后 413 可用，但修复前未做压力测试，不能算已确认 DoS。

## 8. 风险与影响

XSS 可窃取会话/发起操作；/fetch 若被超大响应打中可能拖垮进程，当前只是代码层候选。靶场只在 127.0.0.1，影响低。

## 9. 分诊

- XSS：反射型，需受害者点链接；自建靶场，影响低；已修复。
- /fetch DoS：代码层候选；已加 1MB 上限并验证 413，修复前未验证可利用。
- 设计内 SSRF/XSS/SQLi/IDOR 不重复计漏洞。
